# Подробное руководство Vibe Coding Maestro

> Краткий обзор и быстрый старт: [`README.md`](../README.md).

**Vibe Coding Maestro** помогает вести AI-разработку так, чтобы проект не терял контекст между сессиями, а человек понимал, что происходит и где лежит актуальная информация.

Maestro создаёт готовую структуру проекта, файловую память, правила работы для AI-агентов, безопасную Git-основу и механическую проверку `doctor`. Он не пишет продукт вместо вас и не принимает архитектурные решения. Его задача — дать человеку, Cowork, Claude Code, Codex, Cursor и другим инструментам одну понятную систему координат.

> **Статус:** Vibe Coding Maestro **0.3 beta** (`0.3.0-beta.1`), prerelease. Это строгий **Canonical Engine**: Core создаёт новый канонический проект или повторно проверяет уже валидный проект текущего канона. Core не изменяет непустой неканонический проект; отдельная команда `upgrade` обновляет только доказуемо канонический проект 0.2. Пакет пока не опубликован в npm; команды с `@latest` показывают запланированный публичный интерфейс.

## Зачем нужен Maestro

AI-инструменты хорошо пишут код, анализируют материалы и находят ошибки. Но в долгой работе возникает другая проблема: каждый новый чат или агент видит только часть истории.

Обычно это приводит к знакомому циклу:

1. новая сессия заново изучает проект;
2. человек повторяет уже принятые решения;
3. план, код и документация начинают расходиться;
4. важные ограничения остаются в старом чате;
5. один агент переписывает файл, который должен был только читать;
6. через неделю никто точно не помнит, где остановилась работа.

Maestro выносит рабочий контекст из чатов в обычные Markdown-файлы внутри проекта. Эти файлы читаются человеком и любым AI-инструментом, который умеет работать с файловой системой.

В результате новая сессия начинает не с полного повторного исследования, а с короткой последовательности:

```text
wiki/hot.md
→ discovery
→ открытые аудиты
→ roadmap
→ текущий progress
```

Это помогает экономить не только токены, но и время: меньше повторных объяснений, повторного чтения и повторных ошибок.

## Какую проблему он решает

Maestro соединяет четыре вещи, которые обычно живут отдельно:

- **исследование продукта** — что мы строим, для кого, где факты, а где предположения;
- **реализацию** — код, тесты, сборку и технические решения;
- **память** — актуальный контекст, прогресс, решения и история;
- **проверку** — механические инварианты, аудиты и Git-состояние.

Главная идея проста:

> Чаты и ответы моделей временные. Файлы проекта — общая долговременная память.

### Канон 0.3 beta

Каждый созданный проект получает managed-библиотеку `protocols/` и машинопроверяемый capability ledger. `protocols/build.md` служит router, а `AGENTS.md`, `CLAUDE.md` и `.claude/commands/` остаются тонкими adapters. Интеллектуальные capabilities имеют одного canonical owner и защищены contract anchors.

Глубина выбирается автоматизационной опцией `--depth light | standard | advanced`; интерактивный Guided First Run сохраняет минимум вопросов и использует `standard` по умолчанию. Light, Standard и Advanced — проекции одного канона, а не разные продукты.

При этом память не превращается в одну бесконечную заметку. У каждого типа информации есть своё место и владелец.

## Как устроен полный рабочий цикл

```text
1. Maestro создаёт новый canonical project
                    ↓
2. Человек складывает материалы в maestro/inbox/ и обсуждает идею с агентом
                    ↓
3. /plan (Claude Code) или «план» (Cowork): классификация и черновик плана
                    ↓
4. При необходимости — discovery и read-only инвентаризация исходников
                    ↓
5. Человек проверяет diff и утверждает план: «план утверждаю»
                    ↓
6. preflight: механическая проверка права начинать код
                    ↓
7. /build одной разрешённой порции: код → тесты → проверки → обновление памяти
                    ↓
8. /handoff: фиксируется состояние для следующей сессии
                    ↓
9. Cowork проводит независимый audit
                    ↓
10. Open high/critical findings блокируют doctor
                    ↓
11. Исправления проверены, findings закрыты по стабильным ID
```

До шага 5 действует `CODE_ALLOWED: NO`: агент не утверждает план сам, а молчание согласием не считается.

### Шаг 1. Создать или проверить canonical project

Интерактивный мастер просит принять не больше трёх решений:

1. что сделать: создать новый проект или проверить canonical project;
2. как называется проект или где он находится;
3. с чего начинается работа: идея, материалы, требования или существующий код.

Если при создании ввести только название, Maestro создаст папку на Рабочем столе. Явный путь всегда имеет приоритет.

### Шаг 2. Собрать исходные материалы

Заметки, ссылки, документы и другие входящие материалы регистрируются через:

```text
maestro/inbox/
```

Это зона входящих данных, а не долговременная wiki. Материалы сначала изучаются, затем подтверждённые выводы переносятся в подходящие документы.

### Шаг 3. Провести Cowork Discovery

Готовый runbook находится в:

```text
maestro/runbooks/cowork-discovery.md
```

Cowork должен отделить:

- источники и подтверждённые факты;
- предположения;
- минимальный проверяемый объём продукта;
- то, что не входит в текущий этап;
- открытые вопросы.

Cowork возвращает Markdown, но не изменяет проект напрямую.

### Шаг 4. Импортировать discovery под контролем человека

Человек проверяет результат и сохраняет одобренный текст в:

```text
wiki/concepts/discovery.md
```

Так исследователь не получает право незаметно менять проект, а важные выводы проходят человеческий review.

### Шаг 5. Начать реализацию

AI-инженер читает:

1. `wiki/hot.md`;
2. активный план из `wiki/plans/`;
3. `wiki/concepts/discovery.md`;
4. открытые документы из `wiki/audits/`;
5. `wiki/roadmap.md`;
6. текущие progress-файлы.

После этого он реализует **одну разрешённую порцию** утверждённого плана, запускает тесты, typecheck, build и doctor, а затем обновляет разрешённые разделы wiki. Соседняя порция и следующая фаза сами по себе не начинаются.

### Шаг 6. Передать контекст следующей сессии

Команда `/handoff` создаёт отдельный документ с:

- целью;
- подтверждёнными фактами;
- сделанными изменениями;
- результатами проверок;
- открытыми аудитами;
- рисками;
- точным следующим шагом.

Только `handoff` имеет право обновлять `wiki/hot.md`. Благодаря этому горячий контекст не переписывается случайной командой.

### Шаг 7. Провести независимый аудит

Runbook:

```text
maestro/runbooks/cowork-audit.md
```

Audit хранится в:

```text
wiki/audits/<audit-id>.md
```

Каждая находка получает стабильный ID, severity, target, evidence, status и resolution. `evidence` хранит воспроизводимое доказательство самой находки. Открытые findings уровня `critical` и `high` блокируют успешный doctor.

## Главный путь: от идеи до первой порции кода

Это тот же цикл, но по шагам и с точными командами. Он одинаков для всех задач; меняется только объём планирования.

### Откуда запускать команды

Папок две, и их легко перепутать.

| Что запускаете | Из какой папки | Пример |
|---|---|---|
| `/plan`, `/build`, `/status`, `/wiki`, `/handoff` | из **папки проекта**, открытой в Claude Code | `/plan` |
| `doctor`, `preflight`, `sources`, `upgrade` | из **папки исходников Maestro** (`vibe-coding-maestro`), с `--path` до проекта | `node dist/bin/vibe-maestro.js doctor --path "../Мой проект"` |
| создание нового проекта | из **папки исходников Maestro** | `node dist/bin/create-vibe-maestro.js` |

Служебные команды можно запускать и изнутри проекта — тогда путь указывается до самого CLI, а `--path .` означает текущую папку:

```bash
# из папки проекта
node ../vibe-coding-maestro/dist/bin/vibe-maestro.js doctor --path .
```

После публикации в npm та же команда будет выглядеть так (сейчас не работает):

```bash
npx --package create-vibe-maestro@latest vibe-maestro doctor --path .
```

### Шаг за шагом

1. **Создайте проект** и откройте созданную папку в Claude Code или Cowork.
2. **Обсудите идею** обычными словами. Материалы — заметки, требования, скриншоты — положите в `maestro/inbox/`.
3. **Попросите план.** В Claude Code — команда `/plan`. В Cowork — скажите «план» и используйте runbook `maestro/runbooks/cowork-plan.md`.
4. **Проверьте классификацию.** Агент обязан назвать масштаб, режим, глубину гарантий, риск, профили и причины простым языком. Вы можете принять её, изменить или сузить объём. Если агент говорит «уверенность LOW», сначала ответьте на его вопросы.
5. **Дайте недостающий контекст.** Если материалов мало — discovery по `maestro/runbooks/cowork-discovery.md`. Если есть существующий код — read-only снимок командой `sources`.
6. **Получите черновик.** Для FEATURE и PROJECT это `wiki/plans/<номер>-<слаг>.md` со `status: draft`. Пока план не утверждён, агент показывает гейт:

```text
PLAN: wiki/plans/0002-лендинг.md
STATUS: draft
CODE_ALLOWED: NO
```

7. **Утвердите план сами.** Прочитайте его целиком и скажите «план утверждаю» — или назовите, что нужно изменить. Утверждение проставляет `approved_by` и `approved_at`; агент не имеет права утвердить план за вас.
8. **Проверьте право на код** командой `preflight` (см. ниже). Вывод показывается человеку до первой строки кода.
9. **`/build` ровно одной порции.** Агент берёт порцию из `current_slice`, останавливается на её стоп-гейте и не начинает соседнюю.
10. **Тесты и `doctor`.** Затем `/handoff` — чтобы следующая сессия начала с того же места.

### Адаптивная глубина: не стрелять из пушки по воробьям

| Масштаб | Когда | Что создаётся |
|---|---|---|
| `QUICK` | локальная правка без новой архитектуры, интеграции, данных и смены контракта | mini-plan в `wiki/progress/`; полный пакет планирования не создаётся |
| `FEATURE` | одна законченная возможность существующего проекта | один план `wiki/plans/<номер>-<слаг>.md` |
| `PROJECT` | новый самостоятельный продукт | пакет планирования в одном основном плане + ссылки на discovery и ADR |
| `PROGRAM` / `INTEGRATION` | несколько проектов, репозиториев или фаз | `wiki/programs/<слаг>/`: `program.md`, `source-inventory.md`, `target-architecture.md`, `integration-map.md` и планы фаз |

Лишний артефакт — такая же ошибка, как недостающий. Но масштаб повышается сам, если в задаче обнаружились платежи, персональные данные, авторизация, realtime, миграция или несколько репозиториев — даже если вы просили «быстро».

### Что делает человек, а что агент

| Человек | Агент |
|---|---|
| Ставит цель, границы и non-goals | Собирает вход и предлагает классификацию с причинами |
| Принимает, меняет или сужает классификацию | Пишет черновик плана нужного объёма и делает саморевью |
| Утверждает план и каждую фазу программы | Останавливается на `CODE_ALLOWED: NO` и ничего не утверждает сам |
| Отвечает на блокирующие вопросы | Считает их в `blocking_questions` и не обходит гейт |
| Решает, что мержить, читая diff | Исполняет одну порцию и останавливается на её стоп-гейте |
| Разрешает подключение внешних skills | Только рекомендует capabilities |

### Cowork и Claude Code — две двери в один протокол

Правила планирования живут в одном файле — `protocols/plan.md`. Команда `/plan` и runbook `maestro/runbooks/cowork-plan.md` только направляют туда и не заводят собственных правил.

- **Claude Code** работает внутри проекта: читает файлы, создаёт черновик плана, потом исполняет утверждённую порцию.
- **Cowork** ничего в проекте не меняет: он возвращает Markdown, а человек сам сохраняет его в `wiki/plans/<номер>-<слаг>.md` по шаблону `wiki/plans/TEMPLATE.md` и смотрит diff.

Разные двери, один канон и один и тот же гейт утверждения.

## Два примера: от идеи до первой порции

### Пример A. Простой лендинг

Задача: одностраничный сайт про услугу, форма заявки не нужна, backend не нужен.

1. Создайте проект (`--depth standard`) и откройте папку в Claude Code.
2. Расскажите задачу и вызовите `/plan`.
3. Ожидаемая классификация:

```yaml
scale: PROJECT
mode: GREENFIELD
governance: STANDARD
risk: LOW
profiles: [WEB_UI]
```

4. План — **один документ** `wiki/plans/0002-лендинг.md`. Никакого program pack, никакой отдельной архитектурной библиотеки: для лендинга это бюрократия. Стек обязан быть обоснован, включая явное «база данных и backend не нужны».
5. Порции идут по одной: каркас страницы → контент и адаптивность → состояния загрузки/пустоты/ошибки → метаданные и проверка вёрстки.
6. Утвердите план, запустите `preflight`, затем `/build` первой порции.

Если позже понадобится только поменять текст в готовом блоке — это `QUICK`: mini-plan в `wiki/progress/`, без нового плана.

### Пример B. Игровой портал из двух существующих игр

Задача: у вас уже есть два рабочих проекта — «Дурак» и «Кубики-покер». Нужен общий портал.

1. Создайте **новый** канонический проект портала. Существующие игры в него не копируются.
2. Снимите read-only инвентарь исходников из папки Maestro:

```bash
node dist/bin/vibe-maestro.js sources \
  --path "../Портал" \
  --source "../durak" \
  --source "../dice-poker"
```

3. Вызовите `/plan`. Ожидаемая классификация:

```yaml
scale: PROGRAM
mode: INTEGRATION
governance: ADVANCED
risk: HIGH
profiles: [MULTI_SERVICE_PLATFORM, WEB_UI, GAME]
```

4. Создаётся program pack `wiki/programs/<слаг>/` с планами фаз: оболочка портала → адаптер «Дурака» → адаптер «Кубиков-покера» → общие сервисы.
5. Первая рекомендуемая стратегия — **оболочка вокруг автономных игр** (`wrap`/`adapt`), а не общий runtime. Общий runtime откладывается до третьей интеграции и доказанных повторяющихся контрактов.
6. **Утверждение — пофазное.** Утверждение программы не разрешает будущие фазы:

```text
PROGRAM_APPROVED: YES
CURRENT_PHASE_APPROVED: YES
FUTURE_PHASES_CODE_ALLOWED: NO
```

7. Исходные репозитории остаются нетронутыми: их файлы не переписываются, истории Git не сливаются, deployment и конфигурации не переносятся. Любое изменение чужого проекта — это отдельная утверждённая порция со staging-копией, проверкой отсутствия потерь и откатом.

## Инвентаризация существующих исходников

Команда `sources` отвечает на вопрос «что у нас уже есть» — и ничего не меняет.

```bash
# из папки исходников Maestro; по умолчанию не записывается ничего
node dist/bin/vibe-maestro.js sources --path "../Портал" --source "../durak"

# сохранить снимок как evidence внутри проекта
node dist/bin/vibe-maestro.js sources --path "../Портал" --source "../durak" --write

# заменить прежний снимок этой же команды — только явным решением человека
node dist/bin/vibe-maestro.js sources --path "../Портал" --source "../durak" --write --replace
```

Опции: `--source <путь>` (можно повторять, обязателен хотя бы один), `--write`, `--replace`, `--output <путь>`, `--json`, `--path <путь>`.

- **По умолчанию не пишется ничего.** Снимок существует только в выводе команды; об этом она сообщает прямо.
- **Куда пишется с `--write`:** `maestro/sources/source-inventory.json` внутри канонического проекта; другой путь задаётся `--output`, но только внутри `maestro/sources/` и только `*.json`. Существующий снимок молча не перезаписывается, чужой файл не заменяется вовсе, а versioned hash обновляется в `.maestro/source-hashes.json`.
- **Границы приватности:** содержимое файлов не читается, пути с признаками секретов (`.env`, ключи, `credentials`) пропускаются, symbolic link не раскрываются, обход ограничен по глубине и числу записей с явным объявлением усечения, Git-remote показывается без учётных данных, абсолютные пути в артефакт не попадают, сети команда не касается.
- **Это не converter и не импорт.** Ни один файл источника не копируется, не переносится и не изменяется. Рекомендация `wrap`, `adapt`, `migrate` или `defer` — это `PROPOSAL`; решение принимает человек и переносит его в план.

## Preflight: механический гейт перед кодом

`preflight` отвечает на один вопрос: разрешено ли начинать код прямо сейчас и какая именно порция разрешена.

```bash
# из папки исходников Maestro
node dist/bin/vibe-maestro.js preflight --path "../Мой проект"
node dist/bin/vibe-maestro.js preflight --path "../Мой проект" --json
```

Результат:

| Выход | Вывод | Что значит |
|---|---|---|
| `0` | `Build preflight: разрешено` | план утверждён, объявлена ровно одна порция — можно в `/build` |
| `1` | `Build preflight: заблокировано` | маршрут возвращается в `protocols/plan.md` или к решению человека |

Команда ничего не пишет, ничего не запускает и не читает свободный текст плана: она смотрит только на объявленные поля.

Поля утверждения простыми словами:

| Поле | Что означает |
|---|---|
| `status` | `draft`/`in_review` — код не пишется; `approved`/`active` — план принят человеком |
| `approved_by`, `approved_at` | кто и когда утвердил; без них утверждение не считается состоявшимся |
| `blocking_questions` | сколько вопросов ещё блокирует работу; `0` — ни одного |
| `spec_delta` | `none` — граница не менялась; `open` — менялась и требует повторного утверждения |
| `current_slice` | название ровно одной разрешённой сейчас порции |
| `current_phase_approved` | только для программы: утверждена ли текущая фаза (`yes`/`no`) |

Незаполненное поле означает «неизвестно», а не «ноль»: план без `current_slice` код не разрешает.

Единственное исключение — `QUICK`. Мелкая правка допускается без plan-документа, но все четыре критерия объявляются явно:

```bash
node dist/bin/vibe-maestro.js preflight --path "../Мой проект" \
  --scale quick \
  --quick no-new-architecture,no-external-integration,no-data-change,no-contract-change
```

Частичное объявление исключением не считается — это `FEATURE` и маршрут в `/plan`. Само исключение обязано остаться видимым в `wiki/progress/`.

## Обновление проекта с 0.2 на 0.3

Проект, созданный каноном 0.2, обновляется отдельной командой. Сначала — предложение, в котором не записывается ни один байт:

```bash
# из папки исходников Maestro: dry-run, только показывает список изменений
node dist/bin/vibe-maestro.js upgrade --path "../Мой проект 0.2"
node dist/bin/vibe-maestro.js upgrade --path "../Мой проект 0.2" --json
```

Вывод перечисляет, что будет добавлено, что обновлено, что уже совпадает и что останется без изменений. Если предложение вас устраивает:

```bash
node dist/bin/vibe-maestro.js upgrade --path "../Мой проект 0.2" --apply
node dist/bin/vibe-maestro.js doctor --path "../Мой проект 0.2" --strict
```

Границы применимости:

- обновляется **только доказуемо канонический проект 0.2**: должны совпасть manifest продукта, имя папки, точная форма ownership inventory предыдущего канона и контрольные суммы;
- произвольная папка или чужой манифест отклоняются — это не converter;
- **изменённый managed-файл блокирует обновление целиком** (`upgrade-managed-modified`): команда не перезаписывает вашу правку и не пытается её слить. Сохраните свою версию отдельно, верните файл к каноническому виду и повторите;
- занятый путь нового канона, symbolic link, повреждённые контрольные суммы и оставшийся каталог транзакции тоже блокируют — молчаливого частичного применения не бывает.

Backup и откат:

- всё содержимое готовится в `.maestro/upgrade-staging/` до того, как затронут первый файл проекта; там же лежит backup обновляемых файлов;
- сбой публикации откатывает уже переписанные файлы из backup и удаляет только те каталоги, которые создал сам upgrade;
- файлы, которыми владеет проект (wiki, discovery, прогресс), и история Git не изменяются; ничего не удаляется;
- если каталог транзакции остался после прерванного запуска, команда откажется работать и попросит проверить и удалить его вручную — это защита, а не ошибка.

## Если что-то пошло не так

| Симптом | Что произошло | Что делать |
|---|---|---|
| `preflight-plan-absent`: активного плана нет | в `wiki/hot.md` поле `active_plan: none`, а масштаб больше `QUICK` | вызовите `/plan` и утвердите план; для мелкой правки объявите исключение `--scale quick --quick ...` |
| `preflight-plan-not-approved`: статус `draft` | план ещё черновик | прочитайте план и скажите «план утверждаю» либо назовите правки |
| `preflight-approval-missing` | статус `approved`, но нет `approved_by`/`approved_at` | это не утверждение: попросите проставить след человеческого решения или верните статус в `in_review` |
| `preflight-gate-fields-missing` | план не объявил `blocking_questions`, `spec_delta` или `current_slice` | добавьте поля во frontmatter плана: гейт читает поля, а не текст |
| `preflight-blocking-questions` | остались открытые блокирующие вопросы | ответьте на них сами — агент их не закрывает |
| `preflight-spec-delta`: `spec_delta: open` | граница продукта, данные, безопасность или deployment изменились после утверждения | обновите план и утвердите его заново, затем верните `spec_delta: none` |
| `preflight-phase-not-approved` | утверждена программа, но не текущая фаза | утвердите именно текущую фазу: `current_phase_approved: yes` |
| `write-output-exists` при `sources --write` | снимок уже существует | сравните вывод и добавьте `--replace`, если замена — ваше решение |
| `upgrade-managed-modified` | managed-файл изменён вручную | сохраните свою версию, верните канонический файл, повторите dry-run |
| `upgrade-path-collision` | путь нового канона уже занят вашим файлом | перенесите свой файл и повторите: upgrade ничего не перезаписывает |
| два активных плана | doctor сообщает о нарушении: активным может быть только один план | переведите лишний в `completed` или `superseded` |

Общее правило: закрытый гейт — это возврат в `protocols/plan.md`, а не повод обойти проверку.

## Роли человека, Cowork и AI-инженера

Maestro намеренно разделяет ответственность.

### Человек

Человек принимает решения и контролирует границы:

- выбирает цель проекта;
- принимает или меняет классификацию задачи;
- утверждает план и каждую фазу программы отдельно;
- подтверждает discovery;
- просматривает diff;
- импортирует результаты Cowork;
- принимает или отклоняет архитектурные решения;
- проверяет закрытие audit findings;
- решает, какие внешние skills и команды можно запускать.

### Cowork

Cowork — исследователь и независимый аудитор.

Он:

- изучает материалы;
- отделяет факты от гипотез;
- формирует discovery;
- по runbook `cowork-plan.md` превращает разговор в черновик плана;
- проверяет результат работы;
- создаёт структурированные findings.

Он не пишет код и не изменяет файлы проекта напрямую. Результат всегда возвращается человеку в виде Markdown.

### Claude Code, Codex, Cursor или другой AI-инженер

AI-инженер:

- читает подтверждённый контекст;
- готовит план до гейта утверждения и не утверждает его сам;
- исполняет ровно одну разрешённую порцию;
- пишет код через тесты;
- запускает проектные проверки;
- создаёт progress и technical decisions;
- закрывает findings по стабильным ID после исправления;
- готовит handoff.

Он не переписывает discovery и исходный текст аудитов.

### Maestro

Maestro не является ещё одним «умным агентом». Это установщик, структура и механический контролёр.

Он:

- создаёт предсказуемые файлы;
- закрепляет ownership;
- считает checksums;
- подготавливает Git;
- проверяет инварианты;
- сообщает о расхождениях без обращения к LLM.

## Исходная точка проекта

Maestro предлагает четыре starting point:

- `idea` — пока есть только замысел; сначала нужно определить рамки и критерии успеха;
- `materials` — уже есть заметки, ссылки или файлы; сначала нужно зарегистрировать sources и провести discovery;
- `spec` — требования сформулированы; сначала нужно проверить roadmap, ограничения и открытые вопросы;
- `code` — код уже существует; сначала нужна карта системы и аудит текущего состояния.

Starting point записывается в проект и помогает агентам понять, с какого состояния начинается работа. Это не жёсткий workflow и не запрет менять план позже.

Некоторые каталоги создаются лениво, когда впервые нужны. Это сохраняет структуру понятной и не заставляет пользователя заполнять пустые разделы заранее.

### `AGENTS.md` и `CLAUDE.md`

Это двери для AI-инструментов. В них записаны:

- порядок чтения контекста;
- ownership файлов;
- правила памяти;
- ограничения;
- команда doctor.

Оба файла являются тонкими adapters: они направляют агента в единственные canonical owners внутри `protocols/`, но не дублируют нормативные правила. `AGENTS.md` — универсальная дверь, `CLAUDE.md` — дверь Claude Code.

### `.maestro/`

Служебная зона Maestro:

- `manifest.json` описывает установленную структуру;
- `checksums.json` хранит hashes управляемых файлов;
- `source-hashes.json` фиксирует зарегистрированные source-файлы.

Эти файлы не являются цифровой подписью. Они помогают обнаружить случайный дрейф и несогласованные изменения.

### `maestro/runbooks/`

Здесь лежат готовые инструкции для внешних исследовательских процессов. Сейчас есть discovery и audit.

### `wiki/`

Это общая файловая память проекта. Она не привязана к одному провайдеру или модели и остаётся обычным Markdown в Git.

## Как работает файловая память

### `wiki/hot.md`

Короткий контекст, который нужен прямо сейчас:

- текущая цель;
- подтверждённое состояние;
- главный блокер;
- точный следующий шаг.

Это не полный журнал. Файл должен оставаться компактным. Обновлять его разрешено только через `/handoff`.

### `wiki/plans/`

Планы проекта. Один план описывает одну согласованную порцию работы и живёт по контракту из `wiki/plans/README.md`: frontmatter, состояния, approval metadata и поля build gate. Старые планы не удаляются — новая версия ссылается на предыдущую через `supersedes`. Активный план объявляется полем `active_plan` в `wiki/hot.md`.

### `wiki/concepts/discovery.md`

Подтверждённые рамки продукта:

- sources;
- assumptions;
- MVP;
- non-goals;
- open questions.

Cowork готовит текст, человек импортирует его после review, AI-инженер читает, но не переписывает.

### `wiki/progress/`

Текущее выполнение: что делается, что завершено, какие проверки пройдены и что мешает продолжению. Этой зоной владеет AI-инженер.

### `wiki/decisions/`

Значимые технические решения. В хорошем decision-файле есть контекст, выбранный вариант, альтернативы и последствия.

### `wiki/handoffs/`

Передача состояния между сессиями. Handoff позволяет следующему чату продолжить работу без пересказа всей истории.

### `wiki/audits/`

Независимые проверки с findings по стабильным ID. Исходный текст, ID и evidence находки не переписываются; после исправления обновляются только status и resolution соответствующей находки.

### `wiki/log.md`

Append-only история важных событий. Старые записи не редактируются и не удаляются.

### `wiki/attic/`

Устаревшие материалы. История переносится сюда вместо удаления, если она больше не нужна в активной памяти.

## Команды Claude Code

После создания проекта доступны проектные команды.

### `/status`

Читает hot context, roadmap, discovery и открытые аудиты. Возвращает краткий статус:

- текущая цель;
- что сделано;
- какие проверки пройдены;
- блокеры;
- следующий шаг.

Файлы не изменяет.

### `/plan`

Направляет в `protocols/plan.md` и ведёт планирование до гейта утверждения: собирает вход, предлагает классификацию с причинами, создаёт план нужного объёма и делает саморевью. Кода не пишет и план сам не утверждает — до вашего решения показывает `CODE_ALLOWED: NO`.

### `/build`

Реализует одну разрешённую порцию утверждённого плана:

1. читает контекст, активный план и открытые аудиты;
2. пишет или обновляет тесты;
3. вносит изменение;
4. запускает test/typecheck/build;
5. запускает doctor;
6. обновляет разрешённые части wiki.

### `/wiki`

Сверяет факты работы с файловой памятью.

Разрешено:

- обновлять `wiki/progress/`;
- создавать technical decisions;
- добавлять append-only записи в log;
- переносить устаревшее в attic.

Запрещено:

- изменять `wiki/hot.md`;
- переписывать discovery;
- изменять исходный текст и ID аудитов.

### `/handoff`

Создаёт передачу контекста, обновляет `wiki/hot.md` и добавляет append-only запись в log. Это единственная команда, которой разрешено менять hot context.

## Что проверяет doctor

Doctor — детерминированная проверка без LLM. Он не решает, хороша ли архитектура или верна ли бизнес-идея. Он проверяет то, что можно проверить механически. JSON-отчёт имеет `reportVersion: 1` и стабильную locale-independent сортировку findings. Уровни: `critical`, `error`, `warning`, `info`; обычный режим блокирует critical/error, а `--strict` дополнительно блокирует warning.

Команда после публикации:

```bash
npx --package create-vibe-maestro@latest vibe-maestro doctor --path .
```

Локально из репозитория:

```bash
node dist/bin/vibe-maestro.js doctor --path "/path/to/project"
```

Doctor проверяет:

- существование и структуру manifest;
- строгую runtime-валидность metadata;
- checksums управляемых файлов;
- trusted inventory;
- UTF-8 и frontmatter wiki Markdown;
- локальные wiki-ссылки и выход за границы проекта;
- согласованность `hot.md`, активного progress и активного плана;
- схему, состояния и approval metadata планов в `wiki/plans/`, единственность активного плана и разрешение `supersedes`;
- inbox и source inventory;
- source hashes;
- отслеживаемые Git-файлы `.env`;
- изменённые managed documents;
- структуру audit-файлов;
- открытые findings уровня `critical` и `high`;
- symlink-компоненты в защищённых путях.

Если open high/critical finding существует, doctor завершается с ошибкой. После проверенного исправления статус находки меняется на `resolved`: исходное непустое `evidence` сохраняется, а `resolution` заполняется доказательством исправления. Статус `waived` в контракт 0.3 beta не входит.

У doctor намеренно нет `--fix`. Автоматическое восстановление управляемых файлов могло бы перезаписать полезную пользовательскую работу.

## Безопасность и Git

### Новый проект

Если Git разрешён, Maestro:

- выполняет `git init -b main`;
- создаёт стартовый commit;
- при необходимости задаёт служебную identity только локально для этого репозитория;
- не изменяет глобальные настройки Git;
- оставляет рабочее дерево чистым.

### Существующий Git-репозиторий

Maestro не выполняет `git add -A` и не коммитит пользовательский WIP. Существующий index не должен незаметно измениться.

### Существующие файлы

Maestro не принимает существующий файл за собственный managed-файл и не перезаписывает его молча. Core 0.3 beta отклоняет непустой неканонический проект; присоединение произвольного репозитория возможно только через будущий отдельный Converter.

### Symlink-защита

Защищённые операции проверяют target, его предков и управляемые пути. Symlink-компоненты обрабатываются fail-closed, включая dangling links.

Это снижает риск случайной записи за пределами проекта, но не превращает Maestro в sandbox и не защищает от враждебного процесса с теми же правами.

Полная модель угроз: [`THREAT_MODEL.md`](THREAT_MODEL.md).

## Skill Inventory

Maestro умеет читать metadata project-local skills:

```bash
npx --package create-vibe-maestro@latest vibe-maestro skills --path .
```

Локально:

```bash
node dist/bin/vibe-maestro.js skills --path "/path/to/project"
```

Skill Inventory:

- сканирует только разрешённые project-local каталоги;
- читает `SKILL.md` как данные;
- не исполняет найденный код;
- не следует symlink;
- не устанавливает skills;
- не обращается к сети;
- сообщает о malformed frontmatter и других предупреждениях;
- может показать рекомендации из trusted registry.

Trusted registry сейчас намеренно пуст. В него не добавляются placeholder или непроверенные источники.

## Новый canonical project и будущий Converter

### Создать новый

Подходит, если проекта ещё нет или нужна чистая основа.

Результат:

- новая папка;
- структура Maestro;
- файловая память;
- runbooks и команды;
- Git `main` и стартовый commit, если Git включён;
- green doctor.

### Существующий канонический проект 0.2

Проект, созданный прошлым каноном, обновляется командой `upgrade`: [Обновление проекта с 0.2 на 0.3](#обновление-проекта-с-02-на-03). Это не converter — обновляется только доказуемо канонический проект 0.2 в его собственной папке.

### Существующий неканонический проект

Core 0.3 beta отказывается изменять непустую неканоническую папку даже с `--force`. Проект, который захочет присоединиться к Maestro, в будущем пройдёт через отдельный безопасный **Converter**: read-only анализ → staging-копия → проверка отсутствия потерь → человеческое подтверждение. Converter приводит проект к канону Maestro; Core не адаптируется под legacy-структуру.

### Проверить проект

Интерактивный пункт «Проверить проект» просит только путь: третий вопрос не задаётся. Starting point для doctor не нужен.

## Автоматический запуск и JSON

Для CI или скриптов решения передаются явно:

```bash
npx create-vibe-maestro@latest \
  --yes \
  --target "./My Project" \
  --name "My Project" \
  --start idea
```

Доступные опции:

```text
--target <путь>      куда создать новый canonical project
--name <имя>         отображаемое название
--start <состояние>  idea | materials | spec | code
--depth <глубина>    light | standard | advanced (по умолчанию standard)
--force              повторно обработать только полный валидный canonical project; не обходит отказ и не ремонтирует неполное дерево
--no-git             не создавать Git-репозиторий и стартовый commit
--yes, -y            отключить интерактивный режим
--json               вывести машиночитаемый результат
--help, -h           показать справку
--version, -v        показать версию
```

`--yes` не показывает welcome и не ждёт пользовательского ввода. JSON-режим не добавляет цвет, панели или лишний текст в stdout.

## Честные ограничения

Maestro полезен, но не решает всё.

Он не является:

- sandbox для запуска недоверенного кода;
- цифровой подписью файлов;
- заменой backup;
- защитой от скомпрометированного npm, Git, Node.js или ОС;
- семантическим доказательством правильности кода;
- автоматическим архитектором;
- гарантией, что AI не ошибётся;
- универсальным мигратором любого существующего проекта.

Doctor обнаруживает известные механические расхождения. Он не понимает бизнес-смысл кода и не заменяет тесты, code review и человеческое решение.

Maestro также не устанавливает внешние skills, plugins или MCP-серверы автоматически. Подключение внешнего кода должно быть отдельным осознанным действием с проверкой происхождения, версии, лицензии и checksum.
