# План развития Vibe Coding Maestro

Цель — законченный продукт: человек запускает одну команду, проект разворачивается и дальше живёт без ручного ремонта. План опирается на два независимых ревью версии 0.3.0-beta.3: путь нового пользователя и устройство изнутри.

## Главный шов

Проверки Maestro сравнивают состав файлов проекта с составом той версии, которая их запускает. До 0.3.0-beta.4 проекты звали Maestro через `@latest`, а `upgrade` умел обновлять только с 0.2. Значит, любой выпуск, меняющий состав файлов, сразу покрасил бы проверки во всех проектах, и обновить их было бы нечем. Поэтому первым идёт фундамент обновлений.

## 0.3.0-beta.4 — фундамент

Статус: выпущена 31.10.2026. Состав файлов проекта не меняется, поэтому выпуск ничего не ломает.

- `upgrade` с любой опубликованной версии; прошлые версии и их файлы объявлены в пакете.
- Точная версия Maestro в каждом созданном проекте вместо `@latest`; `upgrade` переписывает её сам. Обёртка `vibe-maestro` зависит от точной версии.
- Вместо `manifest-canonical-mismatch` — понятное сообщение: «проект версии X, проверьте или обновите так».
- Экономный CI: отмена устаревших прогонов, один быстрый прогон на ветке, полная матрица на pull request и `main`, `npm run check` перед пушем.
- Понятные ошибки в `create`, `doctor` и `preflight` вместо stack trace и `ENOENT`.
- README и руководство — только через `npx`, без обещаний, которых код не выполняет.

## 0.3.0 — готовый продукт

Статус: выпущена 31.10.2026 (0.3.0, исправления — 0.3.1). Все изменения состава файлов — одним заходом, с миграцией в `upgrade` с 0.3.0-beta.1 – beta.4 и 0.2.

- Цикл «план утверждён → работа» описан и проверяется; `doctor` и `preflight` не противоречат друг другу по статусу плана.
- Личность проекта — по `project.id`, а не по имени папки; Unicode в путях приводится к NFC. Повторный `create` не переписывает отображаемое имя и даты.
- `doctor` не ругается на то, что велят сами протоколы; `wiki/index.md` принадлежит проекту; есть образцы передачи, ADR и записи хода работы.
- Правила честности — в `.claude/rules/` (файл Maestro), правила проекта — в своём файле рядом; `AGENTS.md` ссылается на те же правила.
- `.claude/settings.json` с запретами по умолчанию: не читать `.env`, не править файлы Maestro; push, publish и удаление — только с вопросом. Файл принадлежит проекту: проект свободно меняет правила, `doctor` и `upgrade` его не трогают. В Claude Code правило «спросить» нельзя перекрыть разрешением из другого файла, поэтому управлять им должен сам проект.
- Правила точечной правки — в `.claude/rules/` рядом с правилами честности: менять минимум, не строить абстракции под один случай, не править тесты ради «зелёного», сначала читать код.
- В шаблоне плана — раздел «Где правим»: какие файлы и модули трогает порция, что проходит через их границы и какой командой порция проверяется.
- `/build` начинает сессию одинаково: `wiki/hot.md` → история Git → прогон проверок до новой работы; после утверждения плана работа идёт в новой сессии.
- Ревьюер и помощник-разведчик для больших файлов только читают (`Read`, `Grep`, `Glob`). Ревьюер сверяет работу с планом, а не стиль; разведчик работает на дешёвой модели и отвечает коротко.
- Навыки: пустые рекомендации убраны; в протоколе есть шаг выбора навыков — установленные, официальные каталоги, чужое только после «да» человека, в плане записано, что взято.
- Изменение плана после утверждения замечается.
- Прерванный `create` оставляет метку и говорит, что убрать.
- Сценарий нового пользователя проверяется автотестом; перед публикацией — независимое ревью.

### Напоминание о новой сессии

- **Правило текстом** в `.claude/rules/maestro.md`, `protocols/build.md` и `protocols/handoff.md`: закрыл порцию — передача дел и предложение начать новую сессию; вторую крупную порцию в той же сессии без согласия человека не начинать. Причина — замер на живом проекте: почти все токены уходят на повторную пересылку истории в длинных сессиях. *Вошло в 0.4.0.*
- **Счётчик `vibe-maestro context`** — размер текущей сессии по журналу Claude Code; агент запускает его при закрытии порции и простыми словами говорит, пора ли в новую сессию. Пороги 40 и 70 % — гипотеза, проверяется повторным замером. *Вошло в 0.4.1.*

### Защиты

- **Раздел «Как подстроить защиты под проект».** *Раздел руководства вошёл в 0.4.0; предложение в `/start` — в 0.4.2.*
  - Четыре уровня: шаблон Maestro → `.claude/settings.json` и `.claude/rules/project.md` проекта (принадлежат проекту) → личный `.claude/settings.local.json` → режим разрешений сессии Claude Code.
  - Порядок правил: deny → ask → allow. `ask` из проектного файла не перекрыть `allow` из личного — только правкой самого `settings.json`.
  - Три-четыре типовые настройки простыми словами. Например:
    - «отправка в облако без вопроса — если репозиторий закрытый и работаете один; `--force` по-прежнему с вопросом»;
    - «свои команды проекта».
  - Разрешения меняются только по «да» человека.
  - «Отправка в облако без вопроса» предлагается в `/start` и только с «да». После этого `ask` остаётся лишь на `git push --force` / `-f`. Для неинтерактивного создания — отдельный флаг. По умолчанию поведение прежнее.
- **Ключи API без поиска файлов.** Запрет `Read(.env)` убран из шаблона `settings.json`; защита от попадания `.env` в git остаётся (`.gitignore`, `doctor`). Человек пишет ключ в чат — агент сам записывает его в `.env` и не повторяет; или «открой окно для ключа» — агент открывает `.env` в редакторе, человек вставляет ключ сам. Честно: написанное в чат остаётся в истории. *Вошло в 0.4.0.*
- **`.gitignore` шаблона:** `.claude/worktrees/` (временные рабочие копии) и `.claude/settings.local.json` — не полагаться на глобальные правила git конкретного компьютера. `upgrade` дописывает только недостающие строки, строки проекта не трогает. *Вошло в 0.4.0.*

### 0.4.2 — старт проекта

- **Знакомство в первой сессии — команда `/start` со своим протоколом `protocols/start.md`.** Для любого проекта. Лучше подробно расспросить в начале, чем спотыкаться потом. `protocols/discovery.md` входит в старт.
  - **Сначала читает, что уже есть:** исходное состояние из `create --start`, материалы, описание, код. Потом проходит все блоки вопросов: найденное показывает с источником и спрашивает «верно?», чего нет — спрашивает.
  - **Как спрашивает:** по одному вопросу, простыми словами. «Не знаю» — нормальный ответ: записывается как UNKNOWN, агент идёт дальше и возвращается к вопросу, только когда без ответа нельзя (например, план не составить). Можно прерваться и продолжить: черновик ответов хранится в проекте. `/start` можно перезапустить, чтобы пересмотреть договорённости.
  - **О задаче:** что делаем; для кого; кому отдаём результат — оставляем себе или передаём (заказчику, команде, работодателю); что значит «готово»; что ещё есть, кроме прочитанного; чего не делаем; ограничения — законы, правила площадок, чужие личные данные. Сроки и бюджет отдельно не спрашиваются: назовёт человек сам — записываются.
  - **Как работаем** — агент предлагает ответ, человек подтверждает или меняет; на «не знаю» действует предложение агента:
    - кто решает и от чьего имени можно писать людям;
    - что только после отдельного «да»: деньги, публикация, отправка в облако, сообщения людям, удаление, чужой код, смена настроек — и что агент делает сам;
    - код после утверждения плана — сразу или по слову человека «начинай» (по умолчанию — ждать слова);
    - как говорить: язык, сколько технических слов, длина ответов, одно решение за раз; что значат FACT / HYPOTHESIS / UNKNOWN — агент объясняет один раз;
    - как отдавать ключи — в чат или в окно, которое откроет агент (оба способа — из 0.4.0); пароли и коды подтверждения вводит человек;
    - где хранится копия проекта и как восстановить его на новом компьютере.
  - **Финал:** сводка на одном экране — ответы, что пока UNKNOWN, ритм работы порциями с передачей дел (правило Maestro, не вопрос); «да» человека; запись: о задаче — `wiki/concepts/discovery.md`, как работаем — `.claude/rules/project.md`, хранение и восстановление — `wiki/restore.md`. Настройки защит в `.claude/settings.json` — только по отдельному «да». Правила честности из `.claude/rules/maestro.md` старт не отменяет и не ослабляет.
  - **`/plan` не переспрашивает:** Stage A читает ответы старта. Старт не пройден — `/plan` предлагает пройти его сейчас; человек может отказаться, тогда план спрашивает только то, без чего план не составить.
- **Один первый шаг везде:** создание → `/start` → `/plan`. Одинаково на экране после создания, в `wiki/hot.md`, в стартовом плане `wiki/plans/0001-starter.md`, в `.claude/rules/maestro.md` и в README. Сейчас эти пять мест называют пять разных первых шагов.
- **Материалы без красной проверки.** У материалов человека одно понятное место; положить их туда, куда велит Maestro, не делает `doctor` красным. Сейчас файл в `maestro/inbox/` даёт `inbox-not-empty` в `--strict`, а файл в `maestro/sources/`, куда советует `maestro/inbox/README.md`, — `source-hashes-missing`. Экран создания, `maestro/inbox/README.md` и `protocols/plan.md` говорят одно и то же.
- **Чужие файлы — байт в байт.** Для папки с чужими данными — `-text` в `.gitattributes`: git не меняет в них переносы строк, свежий клон отдаёт исходные байты.
- **Копия в облаке с первого дня.**
  - Мастер `create` предлагает создать закрытый репозиторий на GitHub — только если есть `gh` и выполнен вход; по умолчанию «нет», для `--yes` — флаг. В мастере по-прежнему не больше трёх решений.
  - `doctor` предупреждает, если у проекта нет remote или есть коммиты, не отправленные в upstream. Проверка идёт по локальным данным git, без сети. Это предупреждение, `preflight` оно не блокирует.
- **Страница «Как восстановить на новом компьютере»** — заготовка `wiki/restore.md`, принадлежит проекту: что лежит в облаке, чего там нет (секреты, `.env`), что поставить, как проверить. `README.md` проекта создаётся только если его нет; существующий не трогается никогда. `upgrade` добавляет только отсутствующее.
- **«Отправка в облако без вопроса»** предлагается в `/start` и включается только с «да» — см. «Защиты».
- **Правила для всех пользователей** в `.claude/rules/maestro.md`:
  - предложение человека сначала сверить с тем, что уже есть, и прямо сказать, если оно не нужно или уже сделано;
  - объяснять простыми словами, на уровне человека; технический термин — только вместе с объяснением.
- **Выбор навыков** в `protocols/plan.md`: искать среди установленных, на GitHub и в официальных каталогах Anthropic; сравнить несколько; проверить, что навык делает (`SKILL.md`, `allowed-tools`, hooks); выбрать лучший и ставить только после «да» человека. Maestro навыки сам не ставит.
- **Для тех, кто создаёт проекты своими скриптами:** признак «старт пройден» описан, и его можно поставить при создании — тогда `/plan` не предлагает старт; названия разделов `wiki/hot.md` не меняются; место для материалов и правило `-text` названы в заметках к выпуску; `create --yes` сам репозиторий не заводит.
- **Паспорт — для того, кому отдаём результат.** Шаблон `wiki/passport.md` говорит прямо: паспорт уходит получателю в `HANDOVER.md`, пишите его для получателя.

### 0.4.3 — проверки, протоколы и исправления команд

- **Проверки с отсечкой.** После проверки остались только мелкие замечания — повторной проверки нет. Есть серьёзные (critical / high) — после правок перепроверяется только исправленное. Доработка правила `protocols/plan.md` «один полный зелёный проход достаточен». Отдельного лёгкого пути не заводим.
- **Маленькая задача доходит до конца без тупика.** Правила для `QUICK` не противоречат друг другу: где лежит мини-план (сейчас `protocols/plan.md` — в `wiki/progress/`, а стартовый план — в `wiki/plans/`), как его закрыть по `protocols/completion.md`, один подтверждённый красный тест на набор вместо «одного контракта за цикл». Строгость проверок следует классификации плана; если она расходится с `depth` проекта — правило «строже из двух» записано явно.
- **Одни метки во всех правилах.** Сейчас в `.claude/rules/maestro.md` их три, в `protocols/plan.md` — шесть, в `wiki/plans/TEMPLATE.md` — четыре по-русски. Одна таблица соответствия.
- **Когда проверять:** аудит плана — до `preflight`, ревью — после порции; `protocols/plan.md` и `protocols/build.md` говорят одно.
- **Правило новой сессии одинаково** в `protocols/plan.md`, `protocols/build.md`, `protocols/handoff.md` и `.claude/rules/maestro.md` — через `vibe-maestro context`.
- **Образец отчёта проверки** `maestro/templates/audit.md` и одна шкала серьёзности у `doctor` и `code-reviewer`.
- **Отметки «готово» в утверждённом плане** не сбивают отпечаток утверждения.
- **Место для отложенных идей (Icebox):** `protocols/wiki.md` его требует, а места нет.
- **«Смените все пароли и ключи»** в `protocols/completion.md` и `HANDOVER.md` — только если в паспорте есть доступы; иначе — «доступов не было».
- **Меньше мелких протоколов:** протоколы в один абзац объединяются с соседними.
- **Экономить минуты GitHub.** Причина — живой проект в закрытом репозитории: сотни прогонов за три недели, больше бесплатного месячного лимита, при том что сами проверки настроены экономно — расходует поведение агента. Правило для агента в любом проекте: проверить на компьютере до отправки; отправлять пачкой — после закрытой порции, а не после каждого коммита; не отправлять, пока прошлый прогон не закончился; не запускать проверки на GitHub вручную вместо локальных; не опрашивать их в цикле. Если проект заводит проверки на GitHub — отмена устаревших прогонов, полный набор только перед слиянием, как в CI самого Maestro.
- **`upgrade` показывает содержимое правок** до `--apply`.
- **`pack`:** `--out` с `/` на конце — папка; перед упаковкой — список того, что попадёт в архив; подсветка внутренних слов и служебных файлов.
- **`context`:** окно модели — из журнала сессии, а не по порогу 200 000 / 1 000 000.

### 0.4.4 — память не разрастается

Причина — живой проект: активный план вырос до сотен строк с десятками правок, а каждая рабочая сессия начинается с него.

- итог порции пишется в её передачу, а в плане остаётся одна строка со ссылкой;
- при превышении порога старые записи журнала переносятся в `wiki/log/ГГГГ-ММ.md`, история не переписывается;
- `doctor` предупреждает о длине `wiki/hot.md`, активного плана, журнала и передач;
- закрытые правки плана и старые аудиты уходят в архив и не читаются целиком.

### Отложено — вернёмся, если появится настоящая проблема

- Команда `vibe-maestro handoff`: передачу делает агент по `protocols/handoff.md`, и это работает.
