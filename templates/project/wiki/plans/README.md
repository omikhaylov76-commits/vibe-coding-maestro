# Планы

Здесь живут планы проекта. План — это документ, который человек утверждает
до написания кода. Один план описывает одну согласованную порцию работы.

- `TEMPLATE.md` — шаблон нового плана: [TEMPLATE.md](TEMPLATE.md).
- `<номер>-<слаг>.md` — сам план, например `0001-starter.md`.

Планы принадлежат проекту: Maestro создаёт стартовый план и больше его не
переписывает. Два файла каталога — этот `README.md` и `TEMPLATE.md` — файлы
Maestro: их обновляет `upgrade`, а не вы; шаблон копируют, а не правят. Старые
планы не удаляются и не затираются — новая версия ссылается на предыдущую через
`supersedes`.

## Frontmatter плана

```yaml
id: PLAN-0001
kind: mini|feature|project|program|phase
status: draft|in_review|approved|active|blocked|completed|rejected|superseded
scale: quick|feature|project|program
mode: greenfield|extension|integration|migration
governance: light|standard|advanced
risk: low|medium|high|critical
profiles: []
created: ГГГГ-ММ-ДД
updated: ГГГГ-ММ-ДД
sources: []
supersedes: null
approved_by: null
approved_at: null
active_phase: null
```

Дополнительно допустимы общие для wiki поля `type` и `title` и отпечаток
утверждения `approved_digest` (см. ниже). Любое другое поле считается ошибкой:
схема закрыта, чтобы опечатка не выглядела как данные.

## Поля build gate

Эти поля необязательны для черновика, но без них утверждённый план не разрешает
код: механический гейт читает поля, а не текст плана.

```yaml
blocking_questions: 0            # неотрицательное целое
spec_delta: none                 # none | open | resolved
current_slice: 01-первая-порция  # ровно одна разрешённая порция или null
current_phase_approved: yes      # yes | no, только для kind: program
```

Отсутствующее поле означает «неизвестно», а не «ноль». Проверка выполняется
командой `vibe-maestro preflight --path .`; она ничего не пишет и не запускает.

## Состояния и утверждение

`draft` → `in_review` → `approved` → `active` → `completed`. Из любого состояния
возможны `blocked`, `rejected` и `superseded`.

- `approved` и `active` обязаны нести `approved_by` и `approved_at` — след
  человеческого решения.
- `draft`, `in_review` и `rejected` не имеют права нести approval metadata.
- В проекте одновременно допустим не более одного плана со `status: active`.
- Активный план объявляется в `active_plan` в [hot.md](../hot.md) и обязан
  лежать в этом каталоге; значение `none` означает, что активного плана нет.
  Объявленный план имеет статус `approved` (утверждён, работа не начата) или
  `active` (работа идёт); план со `status: active` обязан быть объявлен.

### Кто что записывает

Человек утверждает план словами в чате — «план утверждаю». Сразу после этих
слов агент сам записывает поля: человеку не нужно править YAML. Без этих слов
агент поля не трогает, а молчание согласием не считается.

1. `status: approved`, `approved_by: <имя человека>`, `approved_at: <дата>` и
   поля build gate.
2. `active_plan: plans/<файл>.md` в [hot.md](../hot.md).
3. Запуск `preflight` и запись строки «Отпечаток плана» в `approved_digest`.
4. Повторный `preflight`: «разрешено».

Механически Maestro не может отличить, кто заполнил эти поля, — это правило
работы, а не замок.

### Отпечаток утверждения

`approved_digest` — sha256 того, что утверждено: текста плана и его
классификации (`id`, `kind`, `scale`, `mode`, `governance`, `risk`, `profiles`,
`sources`, `supersedes`). Если после утверждения это изменилось, `doctor` и
`preflight` заметят и закроют гейт: изменение показывают человеку и после
повторного «план утверждаю» записывают новый отпечаток. Состояние работы
(`status`, `current_slice`, `active_phase`, даты, поля гейта) в отпечаток не
входит: его меняет сама работа. Отпечаток работает, только если он записан;
пока его нет, `preflight` об этом напоминает. Это сигнализация о незамеченной
правке, а не защита от намеренной подмены.

### Порция закрыта, план выполнен

- Закрыли порцию — `current_slice: null` до решения о следующей; `preflight`
  ответит «порция не выбрана». Следующую выбирают с человеком.
- План выполнен — `status: completed` в плане и `active_plan: none` в
  [hot.md](../hot.md) при передаче.

## Что проверяется механически

`vibe-maestro doctor` проверяет схему, состояния, наличие approval metadata,
единственность активного плана, разрешение `supersedes` внутри этого каталога
и существование объявленных project-relative `sources`. Внешние ссылки в
`sources` (URI со схемой) остаются provenance-записью и на диске не проверяются.

Doctor не оценивает качество идеи и не заменяет человека.

## Как появляется план

Маршрут планирования один — `protocols/plan.md`: разбор входа, классификация,
план нужного объёма, саморевью, аудит по риску и утверждение человеком. В
Claude Code его вызывает команда `/plan`, в Cowork — runbook
`maestro/runbooks/cowork-plan.md`. Оба только направляют в этот протокол.

## Отложено

Program/phase layout (`wiki/programs/<слаг>/`) создаётся вручную по протоколу
и пока не перечисляется doctor: планы вне этого каталога не проверяются, а
`supersedes` принимает только `PLAN-nnnn` из этого же каталога. Поэтому и
`active_plan`, и `preflight` принимают только план отсюда: разрешать сборку по
документу, которого doctor не видит, значило бы выдавать непроверенное за
проверенное.
